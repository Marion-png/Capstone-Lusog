## Architecture

### Student Roster Persistence (invariant)

Adviser-entered student data must survive session expiry, re-login, and server restarts. The database is the source of truth; `session('school_health_card_records')` is only a working copy:

- `AdviserController::store` persists the **full** entry (names, birth date, guardian, address, contact, gender, ...) into the encrypted `student_health_records.student_details` JSON column, alongside the nutrition summary columns.
- `App\Support\StudentRosterSync::syncToSession()` rebuilds the session roster from the DB (scoped to the active institution) and is called by the adviser dashboard, the consent-forms module, and the nurse queue. Any new page that reads `school_health_card_records` must call it first.
- Never treat the session as the only store for new student-entered fields — persist them in `student_details` too.
- `AdviserRosterPersistenceTest` guards this invariant; keep it passing.

### Authentication — Session-Only, No Laravel Auth

This app does **not** use `Laravel\Auth` or the `users` table for login. Authentication is custom and session-based; login accounts live in the database:

- Accounts are rows in the `accounts` table (`name`, `username`, `password_hash`, `role`, `institution_id`, `school_name`, plus adviser `assigned_grade_level` / `assigned_section`). Usernames are unique **per school** (see the Multi-School invariant).
- Login (`POST /login`) looks up the username in `accounts`, verifies the password hash, and on a match writes role data into the session. Active session keys: `active_role`, `active_name`, `active_username`, `active_school_name`, `active_institution_id` (class advisers also get `assigned_grade_level` / `assigned_section`).
- New accounts are self-service: a registration writes a pending row to `account_requests`; the System Admin approves it into `accounts`.
- **Prototype auto-session (local and testing only):** visiting a protected URL without a session does not force a login. `EnsureActiveSession` seeds a demo session for the role that URL belongs to, so any role's UI opens by typing its URL; a real account session is never overwritten. It is governed by `config('app.prototype_sessions')` — on when `APP_ENV` is `local` or `testing`, off everywhere else, `PROTOTYPE_SESSIONS` overrides — because on a reachable deployment it hands every role, System Admin included, and the school's real records to anyone with the link. Off, a protected URL with no session redirects to `/login` (401 for JSON) and a leftover prototype session is flushed. Never turn it on for the deployed service. `PrototypeSessionTest` guards both modes.
- System admin login (`/admin-login`) checks `config('app.system_admin')`, read from the `SYSTEM_ADMIN_USERNAME` / `SYSTEM_ADMIN_PASSWORD` env vars (defaults: `systemadmin` / `admin123` — the deployment sets its own). Never read an env var with `env()` outside `config/`: every deploy caches config, after which `.env` is not loaded.

### Route Guard

`App\Http\Middleware\EnsureActiveSession` — the only login guard. It sits in the global `web` group but acts only on `dashboard`, `adviser`, `nurse` and `health-records` (and everything under them, per `requiresActiveSession()`): a request there with no `active_role` in the session gets a prototype session for the role the URL belongs to (see the auto-session note above), and a prototype session on a URL its role may not view is re-seeded for that role. It sets `no-cache` headers on **every** response, guarded path or not, so browser history never replays an authenticated page after logout.

Two more guards share the `web` group and are described in their own sections: `InstitutionScope` (ejects a scoped role that has no school) and `RestrictSchoolHeadWrites` (refuses every write for `school_head` not on its allow list). `AuditSensitiveAccess` records sensitive reads; `FreshRequestState` is prepended to flush per-request memos.

**The guard asks whether somebody is signed in, never who, so every page and write must check the role itself (invariant).** Several did not: on the deployment any account could open the Feeding Coordinator's dashboard and Beneficiaries (the whole school's learners and flagged names), the School Head's dashboard, the feeding-programme page and every Nutrition Coordinator page, and could rewrite a learner through `/adviser/store`. The test suite could not see it, because prototype sessions are re-seeded as whichever role a URL belongs to, which hides a missing check. `RoleBoundaryTest` signs in as each role with a real (non-prototype) session and requires a clean refusal (302 or 403, never a 200 or a 500); add a new role-owned page to its `PAGES` list. Signing in and signing out both `invalidate()` the session, because it holds the school's roster and these computers are shared (`SessionLifecycleTest`).

### Role System

Roles stored as strings in `session('active_role')`. The eight roles are:

| session value | Description |
|---|---|
| `school_nurse` | **School Nurse** — manages deworming, consultations, health records |
| `clinic_staff` | Consultation logging, medicine inventory; dispenses **paracetamol only** on a consultation (see `DispensingRights`) |
| `clinic_teacher` | **Clinic Teacher** — a teacher covering the school clinic. Reads the School Nurse's screens; dispenses **paracetamol only** and never writes stock (see the Clinic Teacher section) |
| `class_adviser` | Student data entry, medical certificates, consent forms |
| `school_head` | **School Head** — reviews, monitors, approves and exports; never encodes. Read-only over every other write path (see the School Head section) |
| `feeding_coor` | SBFP: uploads attendance (gates the workflow), fills SBFP forms, views auto-tabulated BMI reports |
| `nutricor` | Nutrition analytics, consolidated reports |
| `system_admin` | Account approval/management |

Role checks in controllers are manual string comparisons on `session('active_role')`.

### Account settings (every role, own password only)

`/dashboard/settings` (`SettingsController`, `partials/settings-panels`) answers two questions: which account am I signed in as, and how do I change its password. Before it existed, two rails carried a Settings item pointing at `#` and **nobody in the application could change their password at all**.

It is deliberately not a user management screen. A name, role, school and class assignment are printed and not editable — they are the System Admin's, and a second place to change a role is a second place for two screens to disagree about who somebody is. Four rules hold:

- **The account is resolved from the session, never from the request** (`App\Support\AccountSettings`). Neither route takes an account to act on, so there is no id to swap for somebody else's. Usernames are unique per school, so the lookup is keyed on both.
- **One declaration of what a password is** (`App\Support\AccountPassword`), read by this page *and* by the registration route — a change path with looser rules than registration is a way around them.
- **A missing hash is a hole, and this is the only way to close it.** The login route matches an account whose `password_hash` is empty against *any* password. That is a real state (an approved request can carry a null hash), so Settings offers to **set** one and does not ask for a current password that never existed.
- **The School Head may change their own password.** `settings.password` is on `RestrictSchoolHeadWrites::ALLOWED_ROUTES` as the first kind of entry — how a person gets into or out of the app — because it is the credential their session is made from rather than school data, and it cannot reach another account. The System Admin's credentials are environment variables, so that role is told so instead of being offered a form that could not work.

The page is one body in two shells: the LUSOG rail for seven roles, and `nutricor/settings` for the role whose pages are built on its own layout. `UserSettingsTest` guards all of it. Because the Nutrition Coordinator's layout does not load `lusog-theme.css`, `css/settings.css` styles every component the body uses (card, label, input, button, flash) itself under `.set-page`, so both shells show the same page. That sheet is inlined for every role, so it must never name a role-only panel ("Health Services Offered", "Teaching assignment"): `HealthServicesOfferedTest` asserts other roles' pages do not contain that title.

**The School Nurse's page also carries Health Services Offered** (`partials/settings-health-services`, `settings.health-services`, `App\Support\HealthServicesOffered`, table `health_services_offered`, model `HealthServiceSetting`, Auditable): one switch per `HealthConsentForm::PLANNED_SERVICES` entry, **per school year**, scoped to the nurse's school and refused for every other role. It holds what differs by place — Schistosomiasis and Filariasis medicine and the TAS on Lymphatic Filariasis are given only where those are endemic — so **no Davao City rule is compiled in**; what holds everywhere (Immunization for Grade 7, Iron for female learners) is coded in `ConsentStanding::appliesTo()` and printed beside its switch. A service switched off reads **Not offered** on every consent reading (`forService()`, the reading beside the photo, the upload dialog's locked rows, the nurse's list, the Consent tab). A year with no setting of its own carries the latest earlier year's (else the earliest on record), and says so; a school that never saved one offers everything. Sta. Ana's row starts with those three off (migration `2026_11_09_000001`, and `Institution::seedDefaults()` on a fresh database), never overruling a nurse's saved choice. `HealthServicesOfferedTest` guards it.
### Cross-role live refresh (one stamp, every screen)

Nobody in this application works alone, and nothing anybody submits happens on the screen of the person who needs to see it. A class adviser enrols a learner, uploads a class list and files a consent form; the nurse examines them and logs a consultation; the clinic moves stock; the coordinator marks a feeding day; the head reads all of it. Before this, "submitted" meant "submitted, and now go and tell them" for most of those pairs — only the head's tabs, the coordinator's tabs, the adviser's dashboard and the Medical Documents panel noticed anything.

**One stamp.** `App\Support\SchoolPulse::WATCHED_TABLES` is the school's whole write surface and `stamp()` fingerprints it — row counts and last-touched times, hashed, in **one** `UNION ALL` through `ChangeStamp::forTables()` whatever the number of tables. It is deliberately not per-role: two lists are two answers to "has anything changed", and the role whose list was missing a table is the role that quietly stops seeing a colleague's work. That had already happened — `medical_certificates` was on the adviser's list and not the head's, so a document the adviser filed moved one stamp and not the other. `SchoolHeadPulse` is gone; the class is `SchoolPulse` because the list was always the school's.

**One route and one partial.** `workspace.pulse` (`GET /dashboard/pulse`) serves the stamp to every signed-in role, and `partials/workspace-live` is the include that polls it — no argument, no `$stamp` threaded through a controller, because `ChangeStamp` memoizes per request so a page that already computed the stamp pays nothing extra. The payload is a hash and nothing else, which is what makes it safe to poll every 20s and exempt in `AuditSensitiveAccess`; the heavy, audited re-read happens only when the hash moves. It is scoped to the session's school, so a neighbouring school's write never moves it.

**It never throws away typing.** This is the rule that matters, and the one a later simplification would break. A page is reloaded only when there is nothing on it to lose: `hasWorkInProgress()` refuses the reload if a dialog is open (New Consultation, Receive Stock, Add Medicine), a field is focused, or any form holds an edit against its server-rendered default — and shows a dismissible notice offering **Reload** instead. A roster that refreshes itself under a half-written consultation is worse than a stale one. Never reduce that to an unconditional `location.reload()`; `WorkspaceSyncTest::the_reload_is_held_back_when_there_is_work_in_progress` pins all three cases.

**Who includes it, and who deliberately does not.** Every screen that reads another desk's work: the clinic dashboards (nurse, clinic staff, clinic teacher), health records, the assessment queue, the consultation log, the inventory, both consent-form indexes, both student profiles, the adviser's nutritional status, the head's four reading tabs and every Nutrition Coordinator page (one include on its layout). Three kinds of page are left out on purpose: the **dashboards that re-render their own panels in place** from a metrics endpoint (the head's, the coordinator's and the clinic's Data Visualization, which polls `workspace.pulse` itself — redrawing a panel beats reloading a document), the **Masterlist / Nutritional Health Status list**, where a reload would discard the reader's search and sort, and every page whose whole job is a **form** (`nurse/examine`, `adviser/create`, the parent's consent letter, the paper-consent recorder) — nothing to refresh and everything to lose.

`WorkspaceSyncTest` guards the stamp moving on each kind of write, the per-school scoping, the absence of personal information in the payload, and the list of screens that poll. `DashboardQueryBudgetTest` pins the shared pulse at one query — it is polled by every role on every reading screen, so its cost is paid more often than anything else in the app.
### Routing Pattern

All routes are inline closures or controller actions in `routes/web.php` — no route groups by role and no route-level role middleware. Role checks are manual string comparisons on `session('active_role')` inside the closure or controller; the only blanket enforcement is the global `web` middleware named under Route Guard. Every write route must carry a name (`RestrictSchoolHeadWrites` matches on it, and `SchoolHeadRoleTest` fails an unnamed one).

### Data Layer

- **Deployment:** the app runs on Railway as the `lusog-web` service in project `capstone-lusog`, beside the Postgres service — see `docs/deployment.md`. It is built by Railpack (FrankenPHP), which takes the PHP version from `composer.json` (`^8.4`: the lock file's OpenSpout and Symfony 8 need it), and **migrations do not run on deploy** (`RAILPACK_SKIP_MIGRATIONS=true`): the schema is shared with every developer, so applying one stays a deliberate `php artisan migrate`. The root **`Caddyfile`** replaces Railpack's web-server config: only `public/index.php` executes (the first deploy served a `phpinfo()` page that printed `APP_KEY` and the database password), dotfiles and the Vite manifest answer 404, and static files are browser-cached. **Never put another `.php` file, or anything secret, under `public/`** — `PublicExposureTest` fails the build on it. `App\Http\Middleware\SecurityHeaders` (global) adds nosniff, frame, referrer, noindex and HSTS headers to every application response. **The web service must run in Postgres's region (Southeast Asia)**: in US East every page took 4–13 s of cross-Pacific round trips.
- **Database:** PostgreSQL, deployed on Railway — the only database the app runs against, reached through `DB_URL` (see `docs/railway-database-access.md`). There is no local database and none should be added; the memoization and `DB_PERSISTENT` rules below exist because every query crosses the network. The test suite alone uses in-memory SQLite (`phpunit.xml`).
- **Migrations** live in `database/migrations`; `DatabaseSeeder` seeds institutions, their section catalogue, the condition catalogue and demo accounts.
- **Session storage:** `SESSION_DRIVER=file`, encrypted (`SESSION_ENCRYPT=true`). Session data is in `storage/framework/sessions/`.
- Some data (e.g. deworming requests) falls back to session when its DB table doesn't exist — the routes check `Schema::hasTable()` before querying.
- **Uploaded files** (medical certificates, consent scans, consultation photos) are written through `App\Support\EncryptedFileStorage` to the `local` disk, whose root is `storage/app/private/`. The root `php.ini` is local only (`.railwayignore`), so the deployment's upload limits are set in the root `Caddyfile`; a new limit in the validation rules needs checking against those. **PHP's 30-second `max_execution_time` also applies on the deployment and ends in a fatal error no catch can answer**, so a request that waits on another server calls `App\Support\LongRequest::allow()` first, as the three photo readers do.
- **The server's clock is UTC; the schools' is `config('app.school_timezone')`** (`SCHOOL_TIMEZONE`, default `Asia/Manila`, eight hours ahead). Timestamps are stored in UTC — switching `app.timezone` would misread every one already saved — so a date or time a person reads, types or is greeted by comes from **`App\Support\SchoolClock`** (`now()`, `today()`), never `now()` or `before_or_equal:today` (at 12:14 PM in Davao the server reads 04:14, and before 8 AM its "today" is yesterday), and a stored timestamp is shown after `setTimezone()` to it. `consulted_at` holds the school's wall clock as typed. `SchoolClockTest` pins the first hour of the school day. Still on the server's clock: a medicine's expiry standing (`Medicine::expiryStatus()`), the school-year boundary, and timestamps printed straight from `created_at`.

### Encryption at Rest (invariant)

All personal and sensitive personal information (student names, contact details, medical/health data, consent answers, signatures) is encrypted at rest with AES-256 keyed by `APP_KEY`. Rules to preserve in every change:

- Sensitive model attributes use the custom casts in `App\Casts` — `EncryptedString`, `EncryptedArray`, `EncryptedBoolean`. They always encrypt on write but tolerate legacy plaintext on read (falling back to the raw value instead of throwing `DecryptException`), so pre-encryption rows and empty-string defaults never 500 a page. Do **not** use Laravel's built-in `encrypted` casts here — they throw on plaintext. See the `$casts` arrays on `StudentHealthRecord`, `Consultation`, `StudentHealthCondition`, `MedicalCertificate`, `ParentalConsentForm`, `HealthAssessment`, and `HealthConsentForm` for the authoritative field lists.
- **Never reference an encrypted column in SQL** — no `WHERE`, `ORDER BY`, `GROUP BY`, `DISTINCT`, or aggregate on it. Fetch first, then filter/sort/group on the decrypted collection in PHP. Lookup keys deliberately left plain: `student_id` (LRN), `student_lrn`, `school_name`, `section`, `school_year`, `token`, `status`, `institution_id`, `is_at_risk`, `attendance_sessions_count`.
- **Staff names on `accounts` / `account_requests` are encrypted too.** Both tables are written through `DB::table` (no casts), so every write seals the name with `App\Support\AccountName::seal()` and every read opens it with `AccountName::read()` / `open()`. `username`, `password_hash`, `role` and the assignment columns stay plain: sign-in matches on the username in SQL, and must work whichever `APP_KEY` wrote the student data. Migration `2026_11_10_000004_encrypt_account_names` sealed the names already on file.
- Uploaded documents (medical certificates, signed consent scans) are stored encrypted via `App\Support\EncryptedFileStorage` — use it for any new upload/download, never `storeAs()` + `Storage::response()` directly.
- Sessions are encrypted (`SESSION_ENCRYPT=true`) because adviser-entered student data (addresses, guardians, phone numbers) lives in the session.
- Losing `APP_KEY` means losing the data — treat it as a production secret and never rotate it without re-encrypting (see `2026_07_12_000003_encrypt_existing_sensitive_data.php` for the in-place re-encryption pattern).
- `EncryptionAtRestTest` guards this invariant; keep it passing.

### Audit Trail (invariant)

Every access and action on personal/sensitive personal information is logged to the append-only `audit_logs` table for forensic investigation. Rules to preserve:

- Models holding sensitive data use the `App\Models\Concerns\Auditable` trait — it logs created/updated/deleted with field-level old/new values in the encrypted `details` column. Any new model with personal data must add the trait.
- `App\Http\Middleware\AuditSensitiveAccess` logs page views, API reads, and document downloads on sensitive URL patterns — add new sensitive URL prefixes to its `SENSITIVE_PATTERNS` list.
- Actions that bypass Eloquent (raw `DB::table` writes, e.g. the account routes) must call `App\Support\AuditTrail::record()` explicitly.
- Login, failed login, and logout events are recorded in the login/logout routes.
- The middleware decides **what** to record on the way in and writes the row in `terminate()`, once the response has been sent. A refused write is still recorded exactly as before (the decision was taken before the action ran) — the reader simply no longer waits on an `INSERT` before their page starts rendering.
- Audit entries are evidence: never update or delete `audit_logs` rows from application code (`AuditLog` has no updated_at and no edit path). The System Admin views them at `/dashboard/system-admin/audit-logs`.
- **Immutability is enforced, not only observed** (migration `2026_10_10_000002`). The `AuditLog` model throws on update and delete; database triggers refuse `UPDATE`, `DELETE` and (Postgres) `TRUNCATE` on `audit_logs` from any query, mass queries included; and every entry is sealed on creation with an HMAC over all its fields (`row_hash`, `App\Support\AuditSeal`, keyed from `APP_KEY`). `php artisan audit:verify` and the Audit Trail screen's Seal column report a row altered behind the triggers' back. A test must never clear the trail — count from a baseline (`AuditLog::count()` / `max('id')`) instead; the database will refuse the delete. Rows from before the migration read *Unsealed*, never trusted.
- `AuditTrailTest` and `AuditLogImmutabilityTest` guard this invariant; keep them passing.

### Round Trips Are The Cost (invariant)

This app runs against a hosted Postgres reached through a tunnel, where **one round trip costs the better part of a second**. What makes a screen feel slow here is therefore not how much work it does but how many separate times it asks the database to do some — and that is invisible against the local SQLite the tests use unless something counts it. Four rules:

- **A change-detection pulse costs one query.** Every dashboard polls one every 20s for an answer that is almost always "nothing changed"; the School Head's ran a `COUNT` per watched table — ten round trips, repeated per open tab, with the user's next click queued behind them. `App\Support\ChangeStamp::forTables()` gathers every watched table in a single `UNION ALL` and memoizes the result. Never add a per-table loop to a stamp.
- **A page reads the roster once.** `StudentHealthRecord::rosterFor($institutionId, $schoolYear)` is the one memoized read (`currentYearForInstitution()` delegates to it). Every column worth filtering a roster on is encrypted, so a second fetch is a second decryption of the whole school as well as a second round trip. Same for a session's marks — `FeedingBeneficiarySummary::marksByRecord()` and the coordinator's `marksForSession()` are memoized on the roll they were asked about.
- **A memo is only safe until the data moves, so the write says so.** `RequestMemo::forgetPrefix()` exists for that: `Institution`'s `saved`/`deleted` events drop the per-school cycle and at-risk settings, and `refreshAttendanceRiskFlags()` — which runs after every write to `feeding_attendances` — drops the marks. Add the matching invalidation whenever you memoize something a request can also change. (Note `RequestMemo::remember()` uses `array_key_exists`, not `??=`: a resolver that legitimately returns null must still be cached, or it re-runs on every call.)
- **A list costs a fixed number of queries, whatever its length.** The adviser dashboard once counted shared photos per clinic visit and Medicine Inventory read usage once per medicine, so every week of use made those pages slower. Count for the whole list in one grouped query or memoize the page-wide read (`MedicineUsage::monthlyTotals()`, dropped by `MedicineDispense`'s saved/deleted events). `DashboardQueryBudgetTest::a_clinic_list_does_not_query_per_row` guards it. The 20-second polls also skip `SyncTeacherAssignment`'s account lookup (they read `AuditSensitiveAccess::NON_SENSITIVE_PATTERNS`), which is what keeps a teacher's pulse at one query.
- **Decryption is memoized by ciphertext, not by attribute.** Laravel only caches a cast that returns an *object*, so the `App\Casts` casts — which return strings, arrays and booleans — re-ran a full AES decrypt plus HMAC check on **every single attribute access**, tens of thousands of times per page. `App\Support\DecryptedValues` maps ciphertext → plaintext for the length of the request (flushed by `FreshRequestState`, capped, and caching the legacy-plaintext path too, since that one *throws*). A ciphertext always decrypts to the same plaintext, so a write is self-invalidating: new ciphertext, new key.

`DashboardQueryBudgetTest` and `AdviserDashboardQueryBudgetTest` guard all of this — a pulse must stay at one query and no page may issue the same read twice. `DB_PERSISTENT` (see `config/database.php`) reuses the connection between requests, which is worth several round trips per request against a tunnelled database and nothing at all against a local one.

**On the client, a tab switch issues its request immediately.** The sidebar transition partials used to apply the exit fade and then `setTimeout(…, 340)` before navigating, so every tab click spent a third of a second doing nothing before the request was even sent, on top of however long the page took. The fade now plays *over* the request — the browser keeps painting the old page until the next document commits — so the feedback is unchanged and the delay is gone. Never reintroduce a timeout between a click and its navigation.

### Multi-School Data Separation (invariant)

Data separation covers **all** modules and records — health records, consultations, medicine inventory, deworming, consent forms, health assessments, feeding attendance, and accounts. Rules to preserve in every change:

- Every query that reads or writes school-owned data must be scoped by the session's `active_institution_id`. Use `StudentHealthRecord::forActiveInstitution()` for student lookups by LRN; child tables (certificates, consents, assessments, attendance) inherit scope through their parent record — verify the parent's `institution_id` before serving them (e.g. downloads).
- Rows created for a school must be stamped with `institution_id` from the session.
- Usernames on `accounts` are unique **per school** (`username + institution_id`), not globally: a teacher working in multiple schools holds a separate account per school. Login verifies the password against every account with that username and asks for a school choice (`school_choices` flash + `institution_id` input) when more than one matches.
- `system_admin` is the only unscoped role; `InstitutionScope` middleware ejects scoped roles that have no `active_institution_id`.

### Key Models and Their Scope

- `StudentHealthRecord` — the central model, one row per learner per school year (`student_id` + `institution_id` + `school_year`). Tracks a student across baseline/endline nutrition measurements, feeding enrolment and attendance, conditions, and consent. Scoped per school by `institution_id` — `scopeForActiveInstitution()` for a lookup by LRN, `rosterFor()` / `currentYearForInstitution()` for the memoized roster read. `school_name` is a plain display column, not the scope.
- `Condition` — master catalogue of 34 health conditions, seeded by `ConditionSeeder`. Supports `search()` and `byCategory()` local scopes.
- `StudentHealthCondition` — pivot between `StudentHealthRecord` and conditions; has an `isVerified()` method that checks for an attached `MedicalCertificate`.
- `MedicalCertificate` — one uploaded medical document for a learner, keyed by the plain `student_lrn` + `institution_id` columns. `student_health_condition_id` is **optional**: documents uploaded from the Medical Documents tab of the student profile carry no condition, so never assume `->condition` is present. The class adviser, school nurse, and clinic staff (`StudentMedicalDocuments::UPLOAD_ROLES`) share one list per learner and each sees what the others filed — `uploaded_by_role` records which desk did. The tab is one component (`partials/student-documents-panel` + `-script`, `resources/css/student-documents.css`) included by both profiles; its routes are deliberately under `/health-records/*`, not `/adviser/*`, because `EnsureActiveSession` would switch a prototype nurse session over to `class_adviser` on an adviser URL. An open panel polls `student-documents.pulse` every 20s — a no-PII count+timestamp stamp, exempt in `AuditSensitiveAccess` like the adviser activity pulse — and re-reads the list only when the stamp moves, so each desk sees what the others just filed. The list endpoints return that same stamp alongside `documents`, so an uploader never re-fetches what it just rendered. Files go through `EncryptedFileStorage`; `StudentMedicalDocumentTest` guards upload/preview/download/delete, the cross-role list, and the per-school scoping.
- **A learner's two weigh-ins are one reading.** `App\Support\NutritionalHealthStatus::forRecord()` returns baseline and endline side by side — height, weight, BMI with its BMI-for-age classification, and height-for-age with its own — and is what **both** student profiles' **Nutritional Health Status** tab renders — the nurse's (`renderNutrition` in `student-health-records.blade.php`, carried on the session row by `StudentRosterSync`) and the class adviser's (the tab formerly called *Feeding Status*, served as `meta.nutrition` by `StudentHealthRecordController`), so one learner's figures cannot differ between the two desks that open them. It classifies nothing itself: BMI-for-age is `BmiClassifier::bmiForAge()` and height-for-age is `BmiAssessmentReport::classifyHeightForAge()` — the same functions the DepEd grids count with — and a stored classification always wins over a recomputed one. **A phase nobody measured is blank**, never the other phase's figures and never an estimate; endline height-for-age is stored nowhere, so it is computed from the endline height and age exactly as the Final BMI grid does. The tab reads only: measurements are the class adviser's to enter.

### Frontend

Blade templates with Tailwind CSS 4. No Livewire. Alpine.js is used inline in some views. Vite bundles assets (`npm run build`). The condition search (`resources/views/components/condition-search.blade.php`) is a self-contained Alpine.js component that calls `GET /api/conditions`.

**LUSOG design system.** The Feeding Coordinator, the School Head, the School Nurse and the System Admin share one system; every page in those roles inlines three stylesheets **in this order**: `css/lusog-theme.css`, then its own page sheet (`css/feeding-*.css`, `css/schoolhead.css`, `css/school-nurse*.css`, `css/system-admin.css`), then its rail sheet — `css/role-sidebar.css` for the coordinator/head/admin `.asb-*` panel (`partials/system-admin-sidebar` for the admin; its Control Center is one page, so the rail reaches its sections by in-page jump links, which `partials/role-page-transition` deliberately leaves alone), `css/nurse-sidebar.css` for the nurse's logo-led `.sb-*` rail. The admin's Control Center carries no announcements board: `Announcement::forActiveInstitution()` reads nothing for the unscoped role, so the board could only ever render empty there. `SystemAdminPagesTest` renders all three admin screens over real rows. `lusog-theme.css` owns the palette (`--lg-*`), the app shell, KPI cards, buttons, inputs, tables, the `.badge` status scale and the alert/flash components; a page sheet carries only what is unique to that page and must not redeclare shell or component rules. Green is the brand and the "healthy" signal only — amber is monitoring, orange at-risk, coral critical, teal neutral information; never paint a component green to look on-brand.

- Chart series come from `--series-healthy` / `--series-risk` in the theme (validated pair; re-run the dataviz validator before changing them).
- **Figures have one treatment, declared once.** `--lg-figures` (`tabular-nums lining-nums slashed-zero`) and `--lg-figure-features` in `lusog-theme.css` are applied by a single rule covering `.tnum`, `.num`, `.kpi-value`, `.kpi-hint`, `.badge` and number/date inputs — numbers in this app are read *down* a column (a roster of rates, a stack of KPIs, a BMI grid), and Inter's proportional default lets "1" narrow so a column of rates goes visibly ragged. All three features ship with Inter, so nothing extra loads and figures stay in the same voice as the rest of the UI. `--lg-mono` is the one monospaced stack, for places where a figure is the subject rather than a value in a sentence (the beneficiary record's value column reads it through `--bd-mono`). Set a figure's features by using those tokens, never by re-declaring `font-variant-numeric` on a page sheet.
- Every tab's `<h1 class="page-title">` is one line in two voices: the subject upright in DM Serif Display charcoal, then `<span>` with the section in italic emerald (`Dashboard <span>Feeding Program</span>`). The serif is loaded for page titles **only** — everything else is Inter.
- **A learner's row is the way into their profile — there is no Action column.** On the class adviser's My Students roster the whole row (`tr[data-href]`, focusable, Enter / Space) opens the profile page, which carries Edit Profile (the profile edits nothing on the learner's record; the one thing it files is the parent's signed consent, from the Consent tab's upload dialog); the learner's record rides on the row so the profile's `?edit=LRN` hand-off still opens the edit form. The roster's Baseline and Endline groups each carry **Height-for-Age** beside the BMI status, from `NutritionalHealthStatus`. On the nurse's Student Health Records the row opens the profile dialog the same way.
- **School Nurse pages** use `partials/nurse-lusog-sidebar` and must include `partials/nurse-page-transition` (or an inline equivalent): `nurse-sidebar.css` starts `.sidebar ~ .main` at `opacity: 0` under `html.js`, so a page that never adds `.page-ready` renders blank. Deworming is the one page still on the retired `.nsb-*` rail (`partials/nurse-sidebar`), and it is deliberately absent from the LUSOG rail's nav; `NurseLusogShellTest` covers the converted tabs and `SchoolNurseDashboardTest` keeps the list of unconverted pages, which is expected to reach zero. Health Records, Consultation Log and Medicine Inventory are shared with Clinic Staff and include `partials/clinic-rail`, which renders whichever role's rail the session belongs to, so a clinic-staff click never lands on the nurse's menu.

- The theme also declares `--asb-*` (sidebar) and `--ann-*` / `--clock-*` (announcements board, live-clock pill). Those partials and `role-sidebar.css` read every colour through `var(--token, <fallback>)`; the fallbacks now hold the same LUSOG values as the tokens, so a page cannot drift off-palette by failing to load them. Retheme by changing the token — edit a fallback only to keep it in step with its token, never to give one role a different colour.

**Forest Green + Beige skin, every role.** `css/lusog-skin.css` applies the product palette — primary `#14532D` (rail, headings, card base edge), secondary `#166534` (actions, the italic half of a title), background `#F5F0E6` (the page canvas and nowhere else), cards `#FFFDF7` (cards, tables, boards, top bar), accent `#D4A72C` (small marks only: the clock, the active tab's bar), text `#1F2933` — by re-pointing `--lg-emerald-deep`, `--lg-emerald`, `--lg-ink` and the surface tokens on screen (chart series keep their own validated tokens). Beige must not dominate: lines, table heads and hovers stay a neutral green-grey, and the canvas is lifted by a white glow, with a sprig of leaves and a faint green wash at the foot. Cards and tables sit on that canvas with a soft sage head, headline-number cards on a 4px primary-green base edge (their colour lives in the icon tile; the Nutrition Coordinator's tile-less `.card.stat` keeps its coloured left edge), a frosted card-colour top bar, pill search, an accent-trimmed clock, and a primary-green rail with curved bands at the top and the foot and a soft olive pill for the active tab. It never changes a typeface, size or weight: every page keeps its own type. It is a layer on top, not a theme: `partials/lusog-skin` emits it once (`@once`) and every rail partial (and the Nutrition Coordinator's layout) includes it just before its `<aside>`, so it follows the page, rail and palette sheets and wins by coming last; its selectors carry an `html` prefix to also outrank style blocks printed later in the body. It re-points the surface tokens (`--lg-page`, `--lg-card`, `--lg-border`, `--lg-rail`, the legacy `--bg`/`--card`/`--border`, `--clock-*`, `--ann-*`) and sets `--rail-*`; the announcements and events boards and the retired Deworming rail read those tokens inside their own partials, because the skin must never name `ann-board` or an `nsb-*` class (`SystemAdminPagesTest` and `NurseLusogShellTest` assert their absence by string). Everything is inside `@media screen`, so printed pages stay white, and tables inside `.form-sheet` are excluded so the DepEd facsimile keeps its register. Pages with no rail (sign-in, consent paper, health-assessment sheets, print views) do not get it.

**One palette, every role.** A page is on the palette one of two ways, never both: pages migrated to the design system inline `css/lusog-theme.css`; every other page inlines `css/lusog-palette.css` **after** its own styles, which re-points the older private ramps (`--g900`, `--text-3`, `--border`, …) at LUSOG values. Loading order is the whole mechanism — the palette wins by coming last, so a page that inlines it before its own `:root` silently keeps the old greens. Legacy sheets no longer hardcode hex greens; write new rules against `--lg-*`. `SharedPaletteTest` guards both the coverage and the ordering across all eight roles.

- **The SIGLA logo is two files.** `images/sigla-logo.png` is the full lockup (shield, wordmark, tagline) — every role's rail (`.sb-logo-full`, `.asb-logo-full`, the Nutrition Coordinator's `.sb-logo`, Deworming's `.nsb-logo`), the sign-in, admin sign-in and account-request pages — never an icon-plus-wordmark pair. `images/sigla-mark.png` is the shield alone, square, for every favicon and the 34px consent/assessment topbar, where the stacked lockup would be squeezed unreadable. Both are transparent and drawn for the brand green: the wordmark is white and the shield carries its own green field. A changed logo gets a **new file name**, never new bytes under the old one — Caddy caches `/images/*` for a week, so an overwritten logo keeps showing the old one. `BrandLogoTest` guards every role's pages.
- The dashboard's BMI zone colours (`.grad-under/-healthy/-over` in `feeding-dashboard.css`) are a validated set, not a palette picked by eye. Re-run the dataviz validator before changing any of them — the brief's lighter `#F2B84B` / `#43A866` both fail the CVD and contrast checks as line colours.
- `feeding-sbfp-forms.css` deliberately keeps two registers: app chrome on the system, but `.form-sheet` and everything inside it is a facsimile of the printed DepEd form (black hairlines, uppercase heads). Do not modernise the sheet.

### Test Setup

PHPUnit with an in-memory SQLite DB (configured in `phpunit.xml`, which blanks `DB_URL`), so the suite never reaches the Railway database. Tests use `RefreshDatabase`. Feature tests directly boot the Laravel app — session state must be set manually via `$this->withSession([...])` since there is no Auth facade to log in with.
