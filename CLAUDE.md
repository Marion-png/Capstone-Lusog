This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.


## Architecture

### Student Roster Persistence (invariant)

Adviser-entered student data must survive session expiry, re-login, and server restarts. The database is the source of truth; `session('school_health_card_records')` is only a working copy:

- `AdviserController::store` persists the **full** entry (names, birth date, guardian, address, contact, gender, ...) into the encrypted `student_health_records.student_details` JSON column, alongside the nutrition summary columns.
- `App\Support\StudentRosterSync::syncToSession()` rebuilds the session roster from the DB (scoped to the active institution) and is called by the adviser dashboard, the consent-forms module, and the nurse queue. Any new page that reads `school_health_card_records` must call it first.
- Never treat the session as the only store for new student-entered fields — persist them in `student_details` too.
- `AdviserRosterPersistenceTest` guards this invariant; keep it passing.

### Authentication — Session-Only, No Laravel Auth

This app does **not** use `Laravel\Auth` or the `users` table for login. Authentication is custom and session-based; login accounts live in the database:

- Accounts are rows in the `accounts` table (`name`, `username`, `password_hash`, `role`, `institution_id`, `school_name`, plus adviser `assigned_grade_level` / `assigned_section`). Usernames are unique **per school** (see the Multi-School invariant).
- Login (`POST /login`) looks up the username in `accounts`, verifies the password hash, and on a match writes role data into the session. Active session keys: `active_role`, `active_name`, `active_username`, `active_school_name`, `active_institution_id` (class advisers also get `assigned_grade_level` / `assigned_section`).
- New accounts are self-service: a registration writes a pending row to `account_requests`; the System Admin approves it into `accounts`.
- **Prototype auto-session:** visiting a protected URL without a session does not force a login. `EnsureActiveSession` seeds a demo session for the role that URL belongs to, so any role's UI opens by typing its URL; a real account session is never overwritten. `PrototypeSessionTest` guards this.
- System admin login (`/admin-login`) uses `SYSTEM_ADMIN_USERNAME` / `SYSTEM_ADMIN_PASSWORD` env vars (defaults: `systemadmin` / `admin123`).

### Route Guard

`App\Http\Middleware\EnsureActiveSession` — the only auth middleware. It checks `session()->has('active_role')` and redirects to login if missing. It also sets `no-cache` headers on every response (authenticated or not) to prevent browser history from showing authenticated pages after logout.

Applied to all routes under: `dashboard/*`, `adviser/*`, `nurse/*`, `health-records/*`.

### Role System

Roles stored as strings in `session('active_role')`. The seven roles are:

| session value | Description |
|---|---|
| `school_nurse` | **School Nurse** — manages deworming, consultations, health records |
| `clinic_staff` | Consultation logging, medicine inventory |
| `class_adviser` | Student data entry, medical certificates, consent forms |
| `school_head` | **School Head** — reviews, monitors, approves and exports; never encodes. Read-only over every other write path (see the School Head section) |
| `feeding_coor` | SBFP: uploads attendance (gates the workflow), fills SBFP forms, views auto-tabulated BMI reports |
| `nutricor` | Nutrition analytics, consolidated reports |
| `system_admin` | Account approval/management |

Role checks in controllers are manual string comparisons on `session('active_role')`.

### Feeding Coordinator workflow (attendance-first)

The coordinator's flow is ordered and mostly computed — the period is the `school_year`:

0. **The programme is Junior High only (invariant).** `FeedingBeneficiarySummary::GRADE_LEVELS` (**7–10**) is the single declaration of the grades SBFP covers, and `isEligible($record)` — a covered grade **AND** a qualifying status — is the one test. Senior High is out of scope everywhere it used to leak: no BMI grid, no enrolment candidate, no beneficiary count, and no Grade 11/12 option on the adviser enrolment or account-request forms. Before this, a Grade 11 learner could be enrolled and fed while every report silently dropped them, because `bmiGradeKey()` covered 7–12 and eligibility ignored grade entirely. Never re-type the range — read the constant.
0aa. **A weekend is not a feeding day (invariant).** Nobody is fed on a Saturday or a Sunday, so a weekend is not a session the school missed — it is not a session at all, and counting it stretched every "day N of 120" past where the programme actually was. `FeedingProgramCycle::isFeedingDay()` is the one test and `countFeedingDays()` the one count; `day()` counts the learner's **school days** from the first recorded session, `endDateIso()` is the date of the 120th of them (about 24 calendar weeks out, never `start + 119 days`), and `storeRecordedAttendance` refuses a weekend date outright. The Attendance tab steps over a weekend rather than onto it, says so on the sheet, and offers no way to record one. A legacy weekend mark (written before the guard) is read as the Monday after, so a started programme never reports day 0. `FeedingCoordinatorTabsTest` guards all of it.
0a. **Qualifying is not enrolment (invariant).** The class adviser measures a learner and their nutritional status decides whether they **qualify** (wasted / severely wasted / underweight); the Feeding Coordinator then decides whether to **enrol** them. Only an enrolled learner is a beneficiary — `student_health_records.feeding_enrolled_at` (plain, indexed) with `feeding_enrolled_by` (encrypted staff name). `FeedingProgramController::isEnrolledBeneficiary()` is the one test: the dashboard's panels, the Feeding Program roster and the record-attendance screen all read the enrolled roll, while **attendance import and photo scanning deliberately still match the whole roster** (a sheet is evidence of who was fed; dropping a name for a missing enrolment would lose it). Enrolment happens in the dashboard's modal via `FeedingEnrollmentController` (`candidates` / `store`) — additive, idempotent (re-enrolling is a no-op, never a second stamp), scoped, transactional and audited. **Its scope is required, not optional:** `schoolRecords()` returns nothing without an `active_institution_id` rather than falling through to every school's children, which is what makes the adviser-to-coordinator handover exact — an adviser's entry reaches the waiting list because the adviser stamped their own `institution_id` on it, so it appears for that school's coordinator and no other. The dialog reloads on open and rides the host page's `fc:records-changed` pulse, so a learner measured mid-session appears without a reload. The migration backfilled every already-qualified learner as enrolled at their record's creation, because until then qualifying *was* enrolment. `FeedingEnrollmentTest` guards this.
1. **Attendance first.** Three paths, all landing in `feeding_attendances` inside one transaction (no partial writes), each recording an `AttendanceImport` batch. `AttendanceImport::existsForPeriod()` is the gate.
   - **Spreadsheet:** `importAttendance` parses a DMIRIE-style CSV/XLSX (`App\Support\AttendanceSheetParser` — NAME/GRADE/SECTION + dated columns) and matches rows to learners.
   - **Photograph:** `scanAttendancePhoto` sends the photo to Claude vision **together with the roster** (`App\Support\AttendanceSheetScanner`) so the model matches a mark to an already-known learner instead of reading names cold — deliberately more reliable than blind OCR, and it can't invent a learner. It is never used to identify anyone from a face. Requires `ANTHROPIC_API_KEY`; absent one, the route is disabled and the spreadsheet path is unaffected.
   - **Recorded on site:** `recordAttendanceForm` / `storeRecordedAttendance` (`feedingcor-dashboard/record-attendance.blade.php`) — one screen listing every beneficiary, one tap per learner, one save, reached from the dashboard's "Record Today's Attendance". **It sits under the Attendance tab** — the rail is passed `'active' => 'attendance'` and the breadcrumb leads back there. It used to highlight Feeding Program, the one tab that reads the marks and deliberately offers no way to change one, so the rail named the tab that cannot do what the screen is for; the `#record-attendance` hand-off that opened Feeding Program's upload modal is gone with it. Marks are confirmed on arrival (`SOURCE_MANUAL_ENTRY`, `needs_review` false) and supersede an unread scanned mark for the same session. **A learner left unmarked writes no row at all** — never an absence; the coordinator may simply have skipped them. An absence may carry a `remarks` reason and every mark carries `recorded_by_name` (who took it): both are personal information, cast `EncryptedString`, and because all three bulk writes are **upserts (which bypass model casts)** they are encrypted in the controller with `Crypt::encryptString` — do the same for any column added to those writes. A learner marked present stores no remark. `FeedingRecordAttendanceTest` guards this.
2. **At-risk is derived, never tagged.** Only attendance decides; nutritional status never auto-flags a learner. The rule lives in `App\Support\FeedingAtRiskRule`: `attendance_rate` (default, **< 80%**) or `consecutive_absences` (`config/feeding.php`). The threshold is **school-configurable** — `institutions.feeding_at_risk_threshold`, set per school by the System Admin (`dashboard.system-admin.institutions.at-risk-threshold`, audited); NULL means the app default. Always read it through **`FeedingAtRiskRule::forInstitution($institutionId)`**, never straight from config, or two screens will disagree about who is flagged. `FeedingAtRiskRuleTest` guards the rule, `FeedingAtRiskThresholdTest` the per-school override.
2a. **A rate is not a classification until there is history behind it (invariant).** The threshold applies only after a **minimum observation period** — `minimum_observation_days` (default **10**), school-configurable through the same audited System Admin form (`institutions.feeding_min_observation_days`; NULL = app default, 0 or 1 = classify from the first confirmed session). One of four recorded sessions is 25% and fails every threshold, but four sessions is not a programme problem — it is a sample too small to put a child on a follow-up list over. So the rule has **three exhaustive states** (`FeedingAtRiskRule::status()`): **Early Monitoring** (inside the window), **At Risk**, **On Track**. The window is counted in the learner's own **confirmed** sessions — the very denominator the rate is taken over — never in programme days elapsed, because a feeding day nobody recorded is a missing record, not evidence about that learner. `isAtRisk()` returns false inside the window, so every screen that counts, lists or exports at-risk learners inherits it and none can honour the window while another skips it; `FeedingRiskSeverity` adds a matching `OBSERVING` band that outranks Watch (25% is not "above the threshold") and is excluded from the At-Risk tab's follow-up list. The rate is still computed and shown throughout — the window suppresses the verdict, never the figure. `FeedingAtRiskRuleTest` guards this.
3. **An unconfirmed mark is not an absence (invariant).** `feeding_attendances.is_present` is **nullable**: NULL means a scanned mark no human has confirmed. `FeedingAtRiskRule` excludes NULLs from both the numerator and the denominator, so an unreadable photo can neither flag nor unflag a learner. Never aggregate attendance with `SUM(CASE WHEN is_present ...)` — that folds NULL into "absent". Unclear marks surface in the review queue (`attendanceReviewQueue` → `resolveAttendanceReview`), every resolution is attributed and audit-logged, and the scanned photo is deleted once all its marks are confirmed. `FeedingAttendanceScanTest` guards this.
4. **The dashboard is live, filtered and derived** (`FeedingCoordinatorController::dashboard` → `feed-dashboard.blade.php`). The SBFP header counts the feeding day from `App\Support\FeedingProgramCycle` (day 1 = first recorded session, shared with the Feeding Program page), with the percentage beside the bar. Below it sit four cards (Beneficiary / Attendance / At-Risk / Awaiting Enrollment), an **Attendance Monitoring** panel for today's session and a **Nutritional Status** roll.
   - **Six coordinated filters** (`readFilters`): School Year, Grade, Section, **Sex**, Nutritional Status, Attendance Status. Only the school year is a SQL filter (`school_year` is plain); the rest are applied in PHP because their columns are encrypted. Year/grade/section/sex scope **every** panel; the two status filters narrow the attendance roll alone, so its headline keeps counting everyone expected today. **Sex is read through `FeedingBeneficiarySummary::sexOf()` everywhere** — it lives in the encrypted `student_details.gender` blob and advisers have typed "M", "male" and "Male", so one normalizer is what stops four tabs disagreeing about who is in a filtered roll. Every coordinator surface carries the filter: Dashboard, Attendance, At-Risk, Beneficiaries, the Feeding Program roster and the enrolment dialog. **The filter is labelled "Gender" on screen** — every one of them, plus the School Head's Masterlist and the nurse's Student Health Records — while the query key stays `sex` and the data stays `student_details.gender`; the label is the only thing that changed, so never rename the key to match it. The one place still labelled "Sex" is the DepEd form facsimiles (the BMI grid, Form 1's Master List of Beneficiaries, the head's exported grid), which reproduce printed government paper and must read as it does. Section options are rebuilt server-side for the chosen grade.
   - **Nutritional Status** counts a chosen population by status over `nutritionScale()` — Severely Wasted / Wasted / Normal / Obese / Not measured. Underweight is folded into Wasted (`panelStatus()`) exactly as the DepEd BMI reports do, so the breakdown always sums to the total; Zero rows still render. Two controls sit on it. **Population** (`?population=beneficiaries|all_students`) switches between the programme (qualified **and** enrolled) and **All Students** — every learner in a covered grade, which is the only place a Normal or Obese learner is counted, since they are never beneficiaries and are still the school's children. It moves this panel **alone**: the cards above it are the programme's figures and must not change because somebody widened one breakdown. It is a link group, not a `<select>`, because the panel is replaced wholesale by the live refresh and a select's selection would not survive that. **Endline** is a second count column beside Baseline, never merged with it: it counts only learners actually re-measured, so it may sum to less than the total and reports how many are still to come. Under All Students a learner nobody weighed is **Not measured**, never Normal — `panelStatusOrUnmeasured()` exists for exactly that, because "412 Normal" that quietly includes 60 unweighed children is the one reading this panel must not produce (for beneficiaries the row is always 0: one qualified on a measurement).
   - **Attendance Monitoring** shows Student / Grade / Section / Attendance / Remarks. A recorded session leaves each learner **Present or Absent**; an unread scanned mark and a learner no sheet has covered render as "—", never as an absence. The headline is always `present / expected — %` (greyed until the session is recorded), with chips for the other states.
   - **Attendance At Risk** (`buildAttendanceRisk`) lists the learners under the school's threshold — Student / Grade / Section / Attendance / Days Present / View — worst rate first, above a printed `At-risk threshold: N%`. Days present is counted over **confirmed** sessions, the same denominator the rule judged, so the fraction on screen is the one that decided the flag. The card's At-Risk figure is computed live from the same rule (not the stored `is_at_risk`), so changing the threshold shows immediately. "View" opens `feedingcor-program.attendance.learner` — one learner's sessions, keyed by **record id, never by name** (URLs are logged and shared) and re-scoped to the coordinator's school. "View At-Risk List" goes to the Feeding Program page's at-risk section.
   - **Nutritional Progress** (`App\Support\FeedingNutritionProgress`) plots baseline against endline per status and computes `Improved Nutritional Status: n / total — %`. The rule is **in the business logic, never hand-entered**: improvement means climbing the wasting scale (Severely Wasted → Wasted → Normal); overshooting into Obese/Overweight is deliberately *not* improvement, and the denominator is every beneficiary (not only those measured) so the headline cannot creep up simply because few endline readings exist. Two series on the theme's validated `--series-risk` / `--series-healthy` pair — colour carries baseline-vs-endline, the row label carries the status, every bar is direct-labelled, and a `<details>` table view repeats every number. Re-run the dataviz validator before changing either colour.
   - **Enroll beneficiary** sits on the progress row and opens the enrolment modal (`#enrollBackdrop`) — eyebrow / title / weigh-in line, four client-side filters (name, grade, section, status; names are encrypted so the server cannot search them), per-row **Enroll** and bulk **Enroll selected**, and a footer reading "N currently enrolled · M waiting". It reuses the Feeding Program modal anatomy (`.modal-backdrop` / `.modal-panel` / `-head` / `-body` / `-foot`) so a dialog looks the same product-wide. While open it rides the dashboard pulse (`fc:records-changed`) instead of polling on its own timer, so a learner an adviser measures mid-session appears without a reload; enrolling dispatches `fc:refresh-request` so the cards behind it re-read at once.
   - All five panels are `live-pane`s: the page polls `dashboard.feedingcor.metrics.pulse` (a stamp, no PII — exempt in `AuditSensitiveAccess`) every 20s and re-renders from `dashboard.feedingcor.metrics`, **forwarding its own query string** so a refresh redraws the filtered view. That endpoint returns the **same Blade partials** the first paint used (`feedingcor-dashboard/partials/*`), so live and reloaded views cannot drift. `FeedingCoordinatorDashboardTest` guards this.
5. **The Beneficiaries tab opens on the programme's five figures** (`StudentHealthRecordController::feedingHealthRecords` → `feedingcor-dashboard/feed-healthrec.blade.php`). Under the SBFP header (`SBFP <span>Beneficiaries</span>`, school year, `Active Program:`) sit five cards — Total Beneficiaries / Severely Wasted / Wasted / At Risk / Currently Attending — rendered from `partials/beneficiary-cards` and computed by **`App\Support\FeedingBeneficiarySummary`**, the one place that decides who is a beneficiary (qualified **and** enrolled), which status they are reported under (Underweight folds into Wasted) and how attendance is counted (NULL is unconfirmed and votes neither way). The Dashboard reads the same class, so the two tabs cannot report different programme sizes — `FeedingBeneficiaryCardsTest` guards that equality. The cards follow the tab's grade/section filter and are re-read from `dashboard.feedingcor-health-records.cards` whenever the coordinator's metrics pulse moves; that endpoint returns the same Blade partial the first paint used. Nothing here is stored or hand-entered — never add a card backed by a persisted counter. Under the cards sits a **three-view tab rail** (`partials/beneficiary-tabs`, `?view=all|all_students|at_risk`): **All beneficiaries** (the enrolled roll — always the Total Beneficiaries card), **All Students** (every learner on the roll) and **At risk** (always the At Risk card). `?view=pending` was this middle view's old name, when it listed only the qualified learners waiting to be enrolled; old links still resolve to `all_students`. Each tab carries its count, the counts respect the grade/section filter exactly as the cards do, and the tab filters the table below it — so a tab's number is always the number of rows that view lists (`FeedingBeneficiaryCardsTest` asserts count == rows for all three). Tabs preserve the active filters and the filter form carries the active view, so neither control discards the other's choice. **The table follows the view, and the heading names it** (`Per Beneficiary Comparison` / `All Students` / `Attendance At Risk`). Under `?view=all_students` the roll is replaced by the **whole school roll**: checkbox / Student / Grade / Section / Baseline Status / **Standing** / **Enroll**, with a `#pendingBulk` selection bar for `Enroll selected (n)`. **Only a qualified learner carries the action.** A learner measured Normal, Overweight or Obese is listed with the standing `Not qualified` and **no checkbox and no Enroll button** — the programme feeds the wasted, and this view exists to show the rest of the school, not to widen who may be enrolled. An already-enrolled learner reads `Enrolled` and likewise carries no action, and a row with no database id (the session-fallback case) has nothing to enrol. Both the row action and the bulk button post `record_ids` to **`feedingcor-program.enrollment.store`**, the very endpoint the enrolment dialog uses, so there is exactly one audited, scoped, idempotent path into `feeding_enrolled_at` — never add a second. Under the other two views the table is the coordinator's working list — **# / Student / Grade / Section / Gender / Baseline / Attendance / Status / Endline**. Baseline nutritional status stays because it is *why* the learner is a beneficiary; the BMI figures and the baseline-to-endline delta were removed on purpose — a learner's health profile belongs on the nurse's screen, not here, so do not re-add them. Attendance is the cumulative rate and Status is `Active` / `⚠ At Risk` / `Pending`, both from one `FeedingBeneficiarySummary::attendanceStandings()` reading, so the percentage printed beside a learner is exactly the one that decided their flag. A rate with no confirmed session is an em dash, never 0%. The `#` column is renumbered client-side after every sort and search, so it always reads 1..n for the rows on screen. **Eight coordinated filters** sit under the tabs, in two kinds — the same split the Dashboard uses: **School Year / Grade Level / Section are scope** (they move the cards, the tabs and the table together, and the year is the only SQL filter since `school_year` is plain), while **Sex / Baseline Nutritional Status / Attendance Status / Beneficiary Status / Endline Status narrow the list alone**, so a tab keeps reporting the size of its view rather than the size of the last select touched. Every narrowing filter reads an encrypted column (`student_details.gender`, the status columns) and is therefore applied in PHP after fetch — never as a `WHERE`. Attendance Status reads *today's* session and treats an unconfirmed scanned mark as unmarked, never absent; Endline Status offers "Not yet measured" as a real answer. Options come from `self::STATUS_OPTIONS` / `SEX_OPTIONS` (what the app's classifier actually emits — no "Obese" option that could only return nothing), and an unrecognised value is dropped rather than emptying the page. Three primary actions sit under the header: **Enroll Beneficiaries**, **Export Masterlist** and **Print Masterlist**. **Export Masterlist writes the school's own DepEd form, as a real workbook** (`FeedingMasterlistExportController` → XLSX via OpenSpout): the masterlist heading, the ruled `No. / Name / Grade / Section` table padded to 20 rows, and the `Prepared by / Noted by` block — the same document the SBFP Forms page prints, so an export can be handed in rather than retyped. It is `.xlsx`, not `.csv`, on purpose: a `.csv` is a text file and which program opens one is a setting on the reader's machine that no web app can reach, while an `.xlsx` is a spreadsheet by format and opens in Excel wherever it lands. The page POSTs the **ordered record ids of the rows still on screen** (filtered, searched and sorted), and the controller re-reads and re-scopes them to the coordinator's own institution — ids off the wire decide nothing. With no ids (JS off) it falls back to the enrolled roll for the year on screen (`window.print()` against the `@media print` block in `feeding-healthrec.css`, which drops the rail, topbar and controls). The enrolment dialog is **one shared partial** — `partials/feeding-enroll-modal` plus `css/feeding-enroll-modal.css`, inlined by the Dashboard and this tab; any control marked `[data-enroll-open]` opens it and the endpoints live on `#enrollBackdrop`, never on a button, so a page can offer the action without repeating the wiring. Never copy that dialog into a page.
6. **A learner's name opens their beneficiary record** (`FeedingProgramController::beneficiaryProfile` → `feedingcor-dashboard/beneficiary-detail.blade.php`, `css/feeding-beneficiary.css`). The whole name **cell** is the target on the Beneficiaries tab (`.bnf-name.is-link` zeroes the cell padding and the anchor fills it), so a coordinator aims at the column, not at the glyphs; a session-fallback row with no database id stays plain text. The record is a document, not a tab: `← All beneficiaries`, the eyebrow `BENEFICIARY RECORD`, the name at display weight in **Inter, not the serif** used for page titles, then `Grade — Section · Sex` and `S.Y. … · School-Based Feeding Program`, and a standing plate whose left accent carries the colour (`Active Beneficiary` / `At Risk Beneficiary` / `Pending Enrollment` / `Not a Beneficiary`) on the same scale the roster's badges use. Figures are set in a monospaced face so the value column reads down. Below sits a **three-tab rail — Overview / Attendance / Endline — all rendered in one response**, the rail only choosing what is on screen, so no tab can show a figure the others have moved past (and `@media print` reveals every panel: paper has no tabs). **Overview** = Baseline Nutritional Assessment (height in metres, weight, BMI, BMI status, HFA status — HFA lives in the encrypted `student_details.nutritional_status_height_for_age`, not a column of its own) beside Program (enrolment date, `SBFP <school year>`, `FeedingProgramCycle::DURATION_DAYS`, and days completed = **distinct recorded session dates**, never days elapsed — a day nobody fed is not a feeding day). **Attendance** opens on `present / confirmed days attended` and the rate, over a bar carrying the school's own threshold as a tick — the gap, not the number, is what the eye reads — and an at-risk learner gets an alert naming the rule (`FeedingAtRiskRule::describe()`). Below it the sessions are grouped by month (`sessionCalendar()`), newest month first, as Date / Status / **Recorded By** / Remarks / Correct. The calendar is **the school's feeding days, not the learner's marks**: a day the school fed but no sheet covered this child reads `Not marked`, never an absence, which is the only way a coordinator can see a gap. "Recorded By" is `attendanceAttribution()` — the human who last decided the mark (`reviewed_by_name`), else who recorded it (`recorded_by_name`), else what its `source` says; it is never a guess at a person. **Corrections** post to `feedingcor-program.beneficiary.attendance.correct` (`correctAttendance`), keyed by **learner + session date** so the one path fixes a wrong mark and fills one a sheet skipped. It is coordinator-only, re-scoped to the institution, writes **through the model** (never a raw upsert — the casts are what keep the staff name and remark encrypted), confirms whatever a scan made of the mark, recomputes the at-risk flags, purges a scan photo whose last unclear mark it settled, and records an audit entry carrying **the value it replaced** as well as the new one. The session date must be one the school actually held, so nobody can invent a feeding day for a single learner and quietly change the denominator the rule divides by. **Endline** reports the adviser's closing measurement against the baseline status, or reads "Not yet recorded". Every figure is derived at read time from the same sources the tab reads, so a learner's page and their row can never disagree; the rate is `FeedingAtRiskRule::forInstitution()`'s, an unconfirmed mark votes neither way and is never rendered as an absence, and no rate at all is an em dash. Keyed by **record id, never by name**, and scoped to the coordinator's institution — deliberately *not* to the current school year, since the tab lets the coordinator read an earlier one and the institution is the boundary. Its actions are the coordinator's own: **Print Beneficiary Record** (`window.print()`) and, for a learner still waiting, **Enroll Beneficiary** posting `record_ids` to `feedingcor-program.enrollment.store` — the same one path. Measurements are entered by the class adviser, so this page reports baseline and endline and never asks for them; do not add an endline form or a link to the health profile here. `FeedingBeneficiaryProfileTest` guards this.
7. **Attendance is its own tab** (`FeedingAttendanceController` → `feedingcor-dashboard/attendance.blade.php`, `css/feeding-attendance.css`, sidebar key `attendance`). It answers **who → when → present/absent → cumulative rate → at risk**, and deliberately nothing else: no baseline, BMI, height-for-age, endline, consent or medical column appears here, because a learner's health profile is the Beneficiaries tab's responsibility and two tabs owning one fact is how they start disagreeing (`FeedingAttendanceTabTest` asserts those words never render). One `build()` produces every panel from **one reading of one set of marks**, so the cards, the sheet, the history, the per-beneficiary roll and the calendar cannot contradict each other. **Three figures, three labels, never merged:** five cards (Beneficiaries / Present / Absent / Attendance Rate / At Risk) report the **selected session**, while the programme's **cumulative** rate is named separately on the rate card *with the number of recorded sessions it was taken over* (25% over four sheets is a different claim from 25% over forty), and the feeding day sits in the header. The At Risk card counts the rule's verdict alone; learners still inside the observation period are named on its hint and in their **own `is-info` notice** ("N currently under observation · At-risk classification begins after N recorded feeding days"), never folded into the red at-risk bar — an unclassified learner is not a quieter kind of at-risk. The By Beneficiary roll carries a **Not marked** column (feeding days no sheet covered that learner) beside Present and Absent, so a coordinator reading 1 of 4 can see whether the rest are absences or paperwork, and its Status badge is the rule's three-way state (`Early Monitoring` carries how many more sessions it needs). The attendance filter offers both `at_risk` and `early_monitoring` as cumulative standings that narrow the roll, not the sheet. **The sheet is a record, and recording is a dialog (invariant).** The Attendance Sheet **reports** the marks a session came to and carries no control over them at all — no radio, no remark field, no bulk mark, no save bar. Entering a mark happens in one place, the **Record Attendance dialog** (`partials/attendance-record-modal`, opened by any `[data-record-open]` control, posting to the same `feedingcor-program.attendance.record.store`), and the dialog lists **the whole enrolled roll, unfiltered** — recording through a filtered list would close the day on the learners the filter was hiding, with no way back to them.

   **A recorded session is closed as a whole**, not learner by learner: the first confirmed mark for the date ends it. `canRecord` is false thereafter, the dialog is not rendered, and `sessionIsRecorded()` refuses the endpoint — a stale tab or a replayed form reaches it all the same, and a read-only screen whose endpoint still accepts writes is only a suggestion. That also closes the day for a learner the session skipped: their mark is filled in on their own beneficiary record (`correctAttendance`), where the change is attributed and audited, rather than by two people writing one day from two screens. An **unconfirmed** scanned mark does *not* close a session — nobody has read it, and recording on site is exactly how it gets decided. A weekend closes it too, for a different reason: there was never a session to record. `FeedingRecordAttendanceTest` and `FeedingAttendanceTabTest` guard all of it. Four views on the shared `.seg-tabs` rail: **Attendance Sheet** (the session as a record, searchable, with a tally of what it came to), **Attendance History** (one row per feeding day, newest first, each linking to its sheet), **By Beneficiary** (the cumulative standing the school's threshold is applied to) and **Calendar** (the month, with complete / incomplete / no-session days).

   **The filters split the same way the Dashboard's do, and every view obeys both halves.** Grade, Section and Gender are **scope**: one `inScope()` predicate narrows the roll once in `build()`, and the cards, the sheet, the history, the per-beneficiary roll and the calendar are all derived from that narrowed reading — so a coordinator filtered to one section reads that section's turnout everywhere, rather than one section on the sheet and the whole school in the history, which is what it used to do. Three things are deliberately read off the **unfiltered** roll: `filterOptions` (options built from a filtered list delete the very choice that would widen it again), `sessionLocked` (a session's standing is a fact about the day, and narrowing to one section must never reopen it) and `recordRows` (the dialog lists everyone). **The mark and the standing are two questions, so they are two controls.** **Attendance** offers exactly **All / Present / Absent** (`MARK_FILTERS`), because those are the only three answers a confirmed mark has; "Not yet recorded" and "Unconfirmed" are states a row can be in and are printed on the row, but neither is an answer to "who came today", and a value off the wire that is not on the list is dropped. **Standing** (`STANDING_FILTERS`: at risk / early monitoring) is a verdict across the programme rather than a mark on one day, so it is its own `standing` query key on its own control, rendered **only on By Beneficiary** — the roll it applies to. Folding the two into one dropdown put "Absent" and "At risk (cumulative)" in a single list as though they answered the same question; splitting them is also what keeps the at-risk notice's deep link reachable from a visible control rather than being a URL nobody can get back to. `$pageUrl()` filters **after** the merge, so an override of `''` clears a parameter instead of writing an empty one.

   The mark filter then does two things at once, and both are the same answer to the same question — it narrows the **list** and it narrows the **columns**. On **By Beneficiary** the list is the learners whose mark on the selected session matches (Present and Absent are exclusive, so the two produce disjoint rolls), and the roll carries a `Session · <date>` column printing the mark that put each row there, plus the date picker, because a control that decides what a list contains must not be invisible. On **Attendance History** the list is the sessions carrying that state, while each surviving row still prints its whole tally — a filtered list must not become a wrong one — and History carries its own **Not marked** column beside Present and Absent. In both tables, asking for absences **drops the Present column** and asking for presents drops the Absent one, so a coordinator reads a table of what they asked for rather than hunting the right column in a table of both; **Not marked, Rate and Status never move**, because they answer the same question whichever way the filter is set (`colspan` is computed, never typed). `FeedingAttendanceTabTest` guards all of it. Saving posts to **`feedingcor-program.attendance.record.store`** — the existing audited write path — with `return_to=attendance`; never add a second way to write a mark. A session date outside the running cycle is **refused server-side** (`storeRecordedAttendance` checks the `FeedingProgramCycle` window), because a mistyped year would invent a feeding day and change the denominator every at-risk flag is judged against. The at-risk notice and the threshold come from `FeedingAtRiskRule::forInstitution()`; nothing here is hardcoded. **Export Attendance Sheet** writes the school's own DepEd form as a **workbook, not a dump of the table** — a coordinator who has to merge the title, rule the grid, widen the name column and retype the signature block has not been handed a form they can sign. So the XLSX carries the whole document: the DepEd letterhead merged and centred across the grid, the school and its address, the ruled `NO. | NAME | GRADE | SECTION` head with one upright-rotated column per feeding date (120 days still fit a page), `✓` present / `A` absent / **blank for unmarked** (a blank cell is not an absence), a TOTAL SERVED row, and the Prepared by / Noted by block signed through `SchoolSignatories`. It opens on A4 landscape with the columns already sized. The two seals cannot travel — OpenSpout writes no images — so the letterhead **text** is what makes the exported sheet the same document as the printed one. Live refresh polls the coordinator's existing pulse and re-renders `partials/attendance-*` from `dashboard.feedingcor-attendance.metrics` — **the sheet is deliberately excluded**, since it holds marks nobody has saved yet. Those partials are rendered by two endpoints, so every link inside them is built with the `$pageUrl()` closure against the tab's own route; `request()->fullUrlWithQuery()` there would point dates and tabs at the JSON endpoint.
8. **At-Risk Students is its own tab** (`FeedingAtRiskController` → `feedingcor-dashboard/at-risk.blade.php`, `css/feeding-at-risk.css`, sidebar key `at-risk`). It answers **who is below the school's threshold → why → who needs follow-up**, and it is deliberately not a filtered attendance list: it **reads** the marks the Attendance tab wrote and offers no way to change one, and no way to change an enrolment either — being below the threshold is never a reason to drop a beneficiary, so `Bulk Remove` and any second write path into `feeding_attendances` stay off this page (`FeedingAtRiskTabTest` asserts neither endpoint renders). One `build()` produces the cards and the list from one reading of one set of marks.
   - **Three states, one rule.** `App\Support\FeedingRiskSeverity` layers a monitoring band on `FeedingAtRiskRule` and never replaces it: **At Risk** is the school's business rule (below `FeedingAtRiskRule::forInstitution()`'s threshold) and is the **only** thing the At-Risk Students figure counts; **Critical** is an at-risk learner far below it (`critical_margin_percent`) *or* whose recent sessions are falling (`trend()`); **Watch** is a learner **above** the threshold but inside `watch_margin_percent` — a monitoring aid that must never be added to the at-risk count, or this tab would report a different programme problem than the Dashboard. Both bands are derived from the school's own threshold, so moving the threshold moves them. The list below is the learners who need attention (at risk **and** watch), worst first, with Priority / Student / Grade / Section / Present / Absent / Attendance / Days Remaining / Risk / Follow-Up. A rate with no confirmed session is an em dash, never 0%, and an unconfirmed mark votes neither way — a learner nobody has confirmed a session for is never listed.

The dialog (`#detailBackdrop`) uses the same `.modal-backdrop` / `.modal-panel` / `-head` / `-body` / `-foot` anatomy as the enrolment and follow-up dialogs). Its four panels are the figures against the threshold, a one-sentence `Risk reason` (operational only — never a conclusion about the child), a **cumulative-rate trend chart** with the school's threshold drawn across it (`--series-risk` / `--series-healthy`, the theme's validated pair), the recent absences named by **feeding day**, and the follow-up history. Those panels are **server-rendered per row into a `<template class="ar-detail-source">`** and cloned in on open — so the dialog and the row are one render and cannot disagree, and the record stays out of the document flow and off the printer. The head carries the identity and rate from the row's data attributes, the footer the standing badge and **Record Follow-Up**, which hands over to the follow-up dialog with that learner already selected. The two dialogs are **never stacked**: opening one closes the other.
   - **Follow-up is the one thing here a human enters** — `feeding_follow_ups` via `FeedingFollowUp`, written through the model (the casts are what keep the note and the staff name encrypted), scoped to the institution, audited, and reached from **one dialog and one endpoint** (`feedingcor-at-risk.follow-up.store`) whichever row opens it. Its lifecycle (At Risk → Follow-Up Required → Monitoring → Resolved) runs **alongside enrolment and never touches it**: `Resolved` means the attendance concern was addressed, never that the learner left the programme.

All are applied in PHP — every one reads an encrypted or derived value. **Export At-Risk List** is XLSX via OpenSpout and **Print At-Risk List** uses the sheet's `@media print` block, which keeps the row explanations closed on paper. Live refresh re-renders **the cards only** from `dashboard.feedingcor-at-risk.metrics`; the list is excluded on purpose, because it holds the rows a coordinator has opened to read.

It used to compute its own version of every one of those and disagree with the Dashboard, so: at-risk comes from **`FeedingAtRiskRule::forInstitution()` evaluated live** on the marks (never `AT_RISK_THRESHOLD_PERCENT`, which is gone, and never the stored `is_at_risk`), attendance is **present over confirmed sessions** (never over the calendar program day or the 120-day cycle — a learner is not 3% attended because the programme has 116 days left), and the alert prints the school's own rule with the sessions needed to clear it. **A learner with no baseline has no baseline**: the roster prints an em dash and `No baseline`, never `current − 0.7` — that fallback put a measurement nobody took on a child's record and reported it as improvement. 10. **Printing is a first-class output, and the app shell fights it.** `lusog-theme.css` makes the shell a fixed-height scrolling window (`html, body { height: 100%; overflow: hidden }`, `.main { height: 100vh; overflow: hidden }`, `.content { overflow: auto }`), so a print block that does not reopen those containers prints **one screenful and silently drops the rest of the roster**. Every `@media print` block must set `html, body`, `.main` and `.content` to `height: auto; overflow: visible`, unwrap `.table-scroll` / `.table-card`, and repeat `thead` with `break-inside: avoid` on rows. Colour must not carry meaning on paper — badges print as bordered black text (`.badge::before` off), because a school printer is not to be trusted with the status scale.

A link that can be followed is carried by colour, weight or a tinted hover (`.bnf-name a`, `.risk-view`, `.topbar-bc a`, `.enroll-clear`, the announcement/event delete buttons). The single exception is the DepEd form facsimile in `feeding-sbfp-forms.css` (`.grade-title`) and the consent-form document, which reproduce printed paper and are not app chrome. `FeedingProgramPageTest::nothing_in_the_feeding_program_ui_is_underlined` guards this.

### School Head role (read, decide, export)

**The head reads; other roles write (invariant).** The role reviews, monitors and exports — it never encodes a measurement, adds or transfers a learner, marks a feeding day, touches inventory or edits an account, and since Approve / Return / Lock were removed it records no decision either. That is enforced server-side by `App\Http\Middleware\RestrictSchoolHeadWrites` (last in the `web` group, so a refused write is still audited first): **every** POST/PUT/PATCH/DELETE is refused with a 403 for `school_head` unless its route name is in `ALLOWED_ROUTES`. It is deny-by-default on purpose — a new write route anywhere in the app is refused for this role until somebody adds it deliberately, so the failure mode of forgetting is a head who cannot do something, never a head who silently overwrote a measurement.

The list holds **one** kind of route: how a person gets into or out of the app — `login.submit`, `logout`, `admin.login.submit`, `account.request.submit`. A session is the browser's own, not school data, and *the way out of a role must never be gated on the role*: a session still reading `school_head` (a real head who never signed out, or the demo session `EnsureActiveSession` seeds on any `/dashboard/school-head` URL) would otherwise refuse the very form that replaces it, so signing in as any other role failed with the read-only message. The role's one write over school data — recording a decision on a report — was removed with the Approve / Return / Lock buttons, so **the School Head now writes nothing at all beyond their own session**. Nothing touching a learner's measurement, enrolment, attendance, inventory or an approved account belongs on this list.

**Every write route must carry a name.** An unnamed POST reports its name as `null`, matches nothing on the list, and is refused whatever the list says — which is precisely how signing in broke: `POST /login` was unnamed and the `login` entry named only the GET form. `SchoolHeadRoleTest` fails the build on any unnamed write route, and pins that all six roles plus the System Admin can sign in over a stale head session. (The prototype auto-session is not an exception: `EnsureActiveSession` re-seeds a *demo* session for whichever role a URL belongs to, so a demo head on a coordinator URL has already become a demo coordinator before this middleware runs. A real account keeps its role and is refused — `SchoolHeadRoleTest` pins both.)

**Two readings behind every tab.** `App\Support\SchoolHeadOverview::for($institutionId, $schoolYear)` is the single source for the roster, the feeding programme and the nutritional picture (Dashboard, Feeding Program, Reports, Masterlist), so the Dashboard's undernourishment figure and the Reports tab's cannot drift apart. **Its scope is required, not optional:** without an `active_institution_id` it reads nothing rather than falling through to every school's children, which is what makes the adviser-to-head handover exact — an adviser's entry reaches this head because the adviser stamped their own `institution_id` on it, and a neighbouring school's can never arrive by accident (`InstitutionScope` ejects a scoped role with no school; this is the second lock on the same door). It re-decides nothing the programme already decides: beneficiary from `FeedingBeneficiarySummary::isBeneficiary()`, covered grades from `GRADE_LEVELS`, at-risk from `FeedingAtRiskRule::forInstitution()`, the cycle from `FeedingProgramCycle`, improvement from `FeedingNutritionProgress`. Two rules it adds, both about honesty of measurement:
   - **A learner nobody measured is "Not measured", never Normal.** The coordinator's `FeedingBeneficiarySummary::statusOf()` folds an unrecorded status into Normal so its four cards sum to the beneficiary total; that is wrong for a monitoring report, where "412 Normal" must not include 60 children nobody weighed. `phaseStatus()` returns `''` for an absent reading, `toScale()` returns `''` for anything the classifier does not emit, and every breakdown carries a separate `NOT_MEASURED` bucket. Shares are taken over the learners **measured**, and are NULL — an em dash — when none was: "0% undernourished" over a grade nobody weighed reads as good news about children no one has looked at.
   - **A rate with nothing behind it is undefined, not 0%.** The rehabilitation rate's denominator is every beneficiary (so it cannot creep up as few endlines arrive) but it stays NULL until at least one endline exists. Rehabilitation (`Normal` at endline) and improvement (climbed the wasting scale) are counted separately and never merged.

`App\Support\SchoolHeadHealthOverview::for($institutionId, $schoolYear, $records, $scopedRoster)` is the second: the **clinic, consent and inventory** half, read once and shared by the Dashboard, the Health Overview, Consent Compliance and Inventory tabs for the same reason. It keeps the same two rules (an undefined rate is an em dash; nothing is stored) and adds three of its own:
   - **The period is the school year**, so a head reading last year's oversight never sees this month's clinic traffic folded into it (`periodFor()` — June through May).
   - **Consent is valid only when a parent answered and did not refuse.** Four standings — `valid` / `awaiting` / `declined` / `none` — and a draft nobody sent counts as `none`, because reporting the school compliant on the strength of an unsent letter is the same error as reporting an unweighed learner as Normal. `status` is plain and filters in SQL; `consent_choice` is encrypted and is read after fetch.
   - **The reorder line is each medicine's own `minimum_threshold`**, never a constant here: out / low / monitor / good are all derived from what the clinic set for that item.
   Every grouping runs in PHP — a consultation's learner, grade and complaint are all encrypted at rest, so only `consulted_at`, `status`, `condition_id` and `institution_id` are ever named in a WHERE. `SchoolHeadOversightTest` guards it.
1. **The Dashboard is an oversight and decision-support screen, not an encoding workspace** (`SchoolHeadController`). It answers three questions and nothing else: what is happening in the clinic and the feeding programme, what needs management attention, and whether the school is meeting its health-programme obligations. In order — **the cards first, the filters under them**, because the figures are what the screen is opened for and a row of controls above them sits between the reader and the reading: the executive summary (eight school-level KPIs across every programme — roll, consultations, referrals, beneficiaries, attendance, at-risk, consent completion, stock needing attention), the **Attention required** queue, health-programme performance beside the clinic overview, the feeding programme, the nutritional assessment, consent beside inventory, and the programme overview beside the grade snapshot. **Every queue item is generated from a live condition** — at-risk beneficiaries, learners without valid consent, medicines out of or below their reorder line, unconfirmed scanned marks, today's unrecorded session, feeding days under `SchoolHeadOverview::FULL_TURNOUT_PERCENT`, learners awaiting enrolment, beneficiaries with no baseline, clinic referrals this month, a missing or upcoming endline — never a stored to-do, so an item disappears the moment its condition stops being true. The empty state is a real answer naming where the cycle stands, never a blank box. Eleven panels are `live-pane`s re-rendered from the same Blade partials the first paint used, off the existing pulse (`dashboard.school-head.metrics.pulse`, exempt in `AuditSensitiveAccess`); the refresh **forwards the page's own query string**, or a filtered dashboard would silently redraw itself as the whole school. The audit trail is deliberately **not** in the pulse stamp: every authenticated page view writes to it, so watching it would rebuild the dashboard on every poll. **The head reads what other roles write, so every tab watches for it.** `App\Support\SchoolHeadPulse` declares the tables an adviser, a nurse, the coordinator and the clinic write to, and stamps them per school; the Dashboard re-renders its panels from it, while Health Overview, Consent Compliance, Inventory and Feeding Program include `partials/schoolhead-live` and reload themselves when it moves. Reports and Masterlist deliberately do not: a reload there would discard a half-typed review remark or the head's search and sort.
1a. **Three filters, and they move every panel together.** School year, grade and section (`sectionOptions()` offers every grade and section on the *whole* roll, so one choice never hides the next). Only the school year is a SQL filter; grade and section are applied in PHP through `SchoolHeadOverview::scopedTo()`, which reuses the marks, rule and cycle already fetched — a filtered dashboard costs no second query and cannot judge a learner by a different threshold than the unfiltered one did. A **narrowed roster narrows the clinic figures with it** (`$scopedRoster`): a consultation is matched to a learner by name, the only link the clinic log carries, and a visit matching nobody on a narrowed roll is left out. Unscoped, every visit counts, so a mistyped name can never drop one from the school-wide total. An unrecognised filter value is dropped rather than emptying the page.
2. **The Feeding Program tab reads the marks and offers no way to change one** (`SchoolHeadProgramController`) — a second write path into `feeding_attendances` is how two screens start disagreeing about whether a child was fed. Three readings, no more: the 120-cell grid keyed to **recorded sessions, not calendar days**, the cycle's statistics, and the diverging status chart that aligns every grade on the Wasted/Normal boundary with one shared scale and a Baseline/Latest toggle moving the chart and its callout together. There is **no activity log** — it was removed; the audit trail is the System Admin's screen (`/dashboard/system-admin/audit-logs`), and a second rendering of it here was history without a job.
3. **Reports carries the programme's two charts, and both refuse to draw a reading nobody took.** `buildShiftChart()` is baseline against endline per category on the theme's validated `--series-risk` / `--series-healthy` pair — the same anatomy as the coordinator's Nutritional Progress panel (`.np-*`), so one comparison reads one way product-wide: colour carries *which weighing*, the row label carries the status, every bar is direct-labelled, 2px of surface separates the pair. **The endline series is drawn only once an endline exists** — a row of zeros would read as "every learner left this category", the opposite of "nobody has been re-measured". `buildTurnoutChart()` is turnout month by month, oldest column first, on a **fixed 0–100 axis** (a percentage's scale is not the data's to choose) with `FULL_TURNOUT_PERCENT` drawn across it as a dashed rule, so the gap is the reading; a month whose marks are all unconfirmed draws nothing rather than a zero, and a column below the line changes fill to the theme's generic risk series — never to one of the five `--sh-*` status colours, which mean a child's status and nothing else. Bar widths read against a clean axis (`axisMax()` steps 1/2/5 × 10ⁿ) so a count never lands between two gridlines.
4. **Reports carries two actions — View and Export — and the role writes nothing** (`SchoolHeadReportsController`). Approve / Return for correction / Lock are gone, and with them `ReportReview` and the last write this role had, so the invariant now reads exactly as it is stated: the head reads, monitors and exports; every other role writes. The reports themselves are **derived at read time and never stored**.

   **View opens the report as the form it exports as** (`dashboard.school-head.reports.view` → `schoolhead-dashboard/report-view.blade.php`). Baseline and Endline render the DepEd Nutritional Assessment grid from **`BmiAssessmentReport`** — the one computation the coordinator's SBFP Forms page and the workbook exporter also read, so the form on screen and the file that downloads cannot report different numbers for the same school. Masterlist renders the masterlist form; a monthly report renders its accomplishment table. The page inlines `feeding-sbfp-forms.css` so the facsimile keeps its own register rather than being restyled, and it carries `partials/schoolhead-live`: the figures are derived, so an adviser's weighing recorded while it is open changes what it says.

   **A report is exportable only once its weighing is finished.** `readiness()` is the one rule — baseline needs every learner on the roll measured, endline every beneficiary, the packet both — and it is read by the tab (which offers View but not Export), the view page (which says what is outstanding) and `export()` (which refuses the download). A form with learners still unmeasured is not a draft of the school's return, it is a form that would be wrong when it was handed in; and a button that is not drawn is not a guarantee, so the endpoint checks too. Monthly reports are never gated — they record a month that has already happened. **An export is the school's DepEd form, not a dump of the screen** (`writeAssessmentForm`): the school heading and address line, one ruled BMI grid per covered grade plus the OVERALL grid, then the Prepared by / Attested by / Noted by block — the same sheet the coordinator's SBFP Forms page prints, so a download can be handed in rather than retyped onto the real form. The cells come from **`App\Support\BmiAssessmentReport`**, the one computation both screens read, so the printed form and the exported one cannot report different numbers for the same school and year. The heading is `App\Support\SchoolLetterhead`'s — Republic / Department / Region / Schools Division, the school and its address — the same class the coordinator's printed form and masterlist export read, so all three head the same school the same way. The signature lines carry the school's own staff through `App\Support\SchoolSignatories` (nurse prepares, head notes) and a name the app does not hold prints as a blank line to sign — never an invented signatory. A report the head has already decided on carries that decision, the reviewer's name and the remark; an undecided one prints no review block at all, because an empty one reads as a decision nobody made. The learner list and the outcome figures live on their own **Supporting Data** sheet, so the first sheet stays the form. Exports are XLSX via OpenSpout (the packet is one workbook: Baseline BMI, Final BMI, Accomplishment, Supporting Data); PDF is the print block, as everywhere else in this app. `SchoolHeadReportExportTest` reads the workbook back and guards all of it.
4a. **The outcome cards report the closing weigh-in, and say which children they mean.** Rehabilitated and Rehabilitation Rate were removed. What remains is **Still Severely Wasted and Wasted** — beneficiaries whose *endline* reading is on the wasting scale (`outcome()['still_wasted']`) — beside Improved and Gain at Normal. It is deliberately **not** `still_undernourished`, which is every beneficiary short of Normal and therefore sweeps in the ones nobody re-measured: a child no one has weighed is not evidence either way, so they are counted on the card's hint as "not yet measured" instead. Improvement and rehabilitation stay separate concepts in `SchoolHeadOverview::outcome()` even though the cards no longer print the latter.

5. **Masterlist is read-only and says so** (`SchoolHeadMasterlistController`). Eight filters in the two kinds the coordinator's tabs use — school year, grade and section are scope; sex, baseline, latest, beneficiary standing and attendance standing narrow the list — and every one but the school year is applied in PHP because its column is encrypted. `not_measured` is a real filter answer. A learner's record opens from the whole name **cell** into a dialog cloned from that row's own `<template>`, so the panel and the row are one render; it has no edit control anywhere, because measurements belong to the class adviser and enrolment to the Feeding Coordinator.
6. **Health Overview is the clinic, aggregated** (`SchoolHeadHealthController` → `schoolhead-dashboard/health.blade.php`). Four cards, a monthly activity chart on a clean axis (`axisMax()` steps 1/2/5 × 10ⁿ), disposition and by-grade meters, complaint category and complaint rankings, and the latest visits. **The clinical narrative never appears**: no learner's name, no treatment, no clinic note text — a head reading a management summary has no need for them and the minimum-necessary principle says they should not be handed them (`SchoolHeadOversightTest` asserts a learner's name and their treatment never render). The chart is one neutral series against an axis; colour carries nothing, because a count of visits has no status scale.
7. **Consent Compliance answers a compliance question, never a clinical one** (`SchoolHeadConsentController`). Four cards, completion by section worst-first (the row a head has to chase is the row at the top), and the outstanding learners with their standing. It reports the *standing* of a form and never its contents — the allergies, the write-in exceptions and the parent's signature belong to the adviser and the nurse who act on them. Export is XLSX via OpenSpout, print is the shared `@media print` block.

   **A health-service filter answers the question the other way round.** The catalogue is `HealthConsentForm::SERVICES` — the printed Sulat-Pahibalo's own list, read through `serviceLabels()` and never re-typed — and choosing one (Deworming, say) lists the learners the school **may actually give that service to**: a parent answered, did not refuse, and the letter covered it. That is `consent()['granted_rows']`, and because `services` and `consent_choice` are encrypted at rest the whole filter runs in PHP after fetch. A refusal, an unanswered letter and an unsent draft all authorise nothing and appear on none of it.

   **One signed letter opens on its own page** (`consent-forms.head-show` → `HealthConsentFormController::headShow`, reusing the nurse's read-only view). Reading a monitoring table and opening a named child's parent's signature are different acts, so the second is a deliberate click, refused for an unsigned form, re-scoped to the head's own school, and recorded twice — in `audit_logs` through the `dashboard/*` pattern and on the form's own audit trail. The table beside it still carries standing and service only. `SchoolHeadConsentServicesTest` guards this.
8. **Inventory Overview is stock and standing, and nothing else** (`SchoolHeadInventoryController`). The role has `medicine.view-inventory` but not receipt or dispensing, so the page renders no receive form, no dispense action and no adjustment — and `RestrictSchoolHeadWrites` refuses those endpoints regardless of what a page renders. **The dispensing log is deliberately absent**: it names the learner a medicine went to and why, which is clinical information about a child, and "are we running out of paracetamol" does not need it.
9. **The status fills are a validated five-slot set** (`--sh-sw` / `--sh-w` / `--sh-n` / `--sh-ow` / `--sh-ob` in `schoolhead.css`). Normal and Overweight reuse the theme's already-validated `--series-healthy` / `--series-risk` unchanged; the other three were stepped against them and the whole set passes all six dataviz checks on the card surface. Re-run the validator before changing any of them.

### Routing Pattern

All routes are inline closures or controller actions in `routes/web.php` — no route groups by role. Permission checks inside closures and controllers gate access manually. There is no route-level role middleware.

### Data Layer

- **Database:** SQLite (`database/database.sqlite`), 52 migrations.
- **Session storage:** `SESSION_DRIVER=file`. Session data is in `storage/framework/sessions/`.
- Some data (e.g. deworming requests) falls back to session when its DB table doesn't exist — the controllers check `Schema::hasTable()` before querying.
- **Uploaded files** (medical certificates, parental consent forms) are stored in `storage/app/private/` using Laravel's `private` disk.

### Encryption at Rest (invariant)

All personal and sensitive personal information (student names, contact details, medical/health data, consent answers, signatures) is encrypted at rest with AES-256 keyed by `APP_KEY`. Rules to preserve in every change:

- Sensitive model attributes use the custom casts in `App\Casts` — `EncryptedString`, `EncryptedArray`, `EncryptedBoolean`. They always encrypt on write but tolerate legacy plaintext on read (falling back to the raw value instead of throwing `DecryptException`), so pre-encryption rows and empty-string defaults never 500 a page. Do **not** use Laravel's built-in `encrypted` casts here — they throw on plaintext. See the `$casts` arrays on `StudentHealthRecord`, `Consultation`, `StudentHealthCondition`, `MedicalCertificate`, `ParentalConsentForm`, `HealthAssessment`, and `HealthConsentForm` for the authoritative field lists.
- **Never reference an encrypted column in SQL** — no `WHERE`, `ORDER BY`, `GROUP BY`, `DISTINCT`, or aggregate on it. Fetch first, then filter/sort/group on the decrypted collection in PHP. Lookup keys deliberately left plain: `student_id` (LRN), `student_lrn`, `school_name`, `section`, `school_year`, `token`, `status`, `institution_id`, `is_at_risk`, `attendance_sessions_count`.
- Uploaded documents (medical certificates, signed consent scans) are stored encrypted via `App\Support\EncryptedFileStorage` — use it for any new upload/download, never `storeAs()` + `Storage::response()` directly.
- Sessions are encrypted (`SESSION_ENCRYPT=true`) because adviser-entered student data (addresses, guardians, phone numbers) lives in the session.
- Losing `APP_KEY` means losing the data — treat it as a production secret and never rotate it without re-encrypting (see `2026_07_12_000003_encrypt_existing_sensitive_data.php` for the in-place re-encryption pattern).
- `EncryptionAtRestTest` guards this invariant; keep it passing.

### Audit Trail (invariant)

Every access and action on personal/sensitive personal information is logged to the append-only `audit_logs` table for forensic investigation. Rules to preserve:

- Models holding sensitive data use the `App\Models\Concerns\Auditable` trait — it logs created/updated/deleted with field-level old/new values in the encrypted `details` column. Any new model with personal data must add the trait.
- `App\Http\Middleware\AuditSensitiveAccess` logs page views, API reads, and document downloads on sensitive URL patterns — add new sensitive URL prefixes to its `SENSITIVE_PATTERNS` list.
- Actions that bypass Eloquent (raw `DB::table` writes, e.g. the account routes) must call `App\Support\AuditTrail::record()` explicitly.
- Login, failed login, and logout events are recorded in the login/logout routes.
- Audit entries are evidence: never update or delete `audit_logs` rows from application code (`AuditLog` has no updated_at and no edit path). The System Admin views them at `/dashboard/system-admin/audit-logs`.
- `AuditTrailTest` guards this invariant; keep it passing.

### Multi-School Data Separation (invariant)

Data separation covers **all** modules and records — health records, consultations, medicine inventory, deworming, consent forms, health assessments, feeding attendance, and accounts. Rules to preserve in every change:

- Every query that reads or writes school-owned data must be scoped by the session's `active_institution_id`. Use `StudentHealthRecord::forActiveInstitution()` for student lookups by LRN; child tables (certificates, consents, assessments, attendance) inherit scope through their parent record — verify the parent's `institution_id` before serving them (e.g. downloads).
- Rows created for a school must be stamped with `institution_id` from the session.
- Usernames on `accounts` are unique **per school** (`username + institution_id`), not globally: a teacher working in multiple schools holds a separate account per school. Login verifies the password against every account with that username and asks for a school choice (`school_choices` flash + `institution_id` input) when more than one matches.
- `system_admin` is the only unscoped role; `InstitutionScope` middleware ejects scoped roles that have no `active_institution_id`.

### Per-Section Adviser Scope (invariant)

A class adviser is scoped **twice**: to their school, and within it to one class. `assigned_grade_level` + `assigned_section` on their account are the whole scope — every adviser surface (dashboard roster via `StudentHealthRecordController::loadAdviserContext`, consent forms, health assessments, medical certificates, the student profile) filters `school_health_card_records` and the DB records to that one `"Grade 7 / MATIYAGA"` pair, and `AdviserController::store` overwrites whatever grade/section was posted with the session's own. Two advisers at the same school never see each other's learners.

Which makes the pair a **choice, not a typed answer**: "MATIYAGA", "Matiyaga" and "Matiyaga " are three different classes to every one of those filters, so an adviser who mistypes their own section silently gets an empty roster they cannot explain.

- **`institution_sections`** is each school's own published list — `institution_id` + `grade_level` + `name`, unique together. Nothing here is personal information (a section name is school structure, not a fact about a child), so every column is plain and may be used in SQL. `InstitutionSectionSeeder` carries Sta. Ana National High School's four grades transcribed from its section report.
- Registration cascades: picking a school loads `api.institutions.sections`, which fills the grade dropdown from the grades that school actually runs and the section dropdown from the grade chosen. `grade_level` uses the same `"Grade 7"` label the roster stores in its section string, so a catalogue choice and an adviser's assignment compare directly.
- The server re-checks it — `InstitutionSection::canonical()` in the `account.request.submit` route — and **stores the catalogue's own spelling**, so every adviser at one school is scoped by the same string no matter how they typed it. Never trust the dropdown alone.
- **A school with no catalogue is accepted as typed.** Not every school has published its sections, and refusing them a registration would be worse than accepting a typed answer, so the form falls back to the generic grade list and a text box. Never make the catalogue a hard requirement for registering.
- `InstitutionSectionCatalogTest` guards this, including the two-advisers-one-school separation itself.

### Key Models and Their Scope

- `StudentHealthRecord` — the central model. Tracks a student across baseline/endline nutrition measurements, feeding attendance, conditions, and consent. Filtered by `school_name` (string) to scope per school.
- `Condition` — master catalog of 32 health conditions, seeded by `ConditionSeeder`. Supports `search()` and `byCategory()` local scopes.
- `Consultation` — belongs to a `Condition`. Created by clinic staff/nurse during clinic visits.
- `StudentHealthCondition` — pivot between `StudentHealthRecord` and conditions; has an `isVerified()` method that checks for an attached `MedicalCertificate`.
- `MedicalCertificate` — one uploaded medical document for a learner, keyed by the plain `student_lrn` + `institution_id` columns. `student_health_condition_id` is **optional**: documents uploaded from the Medical Documents tab of the student profile carry no condition, so never assume `->condition` is present. The class adviser, school nurse, and clinic staff (`StudentMedicalDocuments::UPLOAD_ROLES`) share one list per learner and each sees what the others filed — `uploaded_by_role` records which desk did. The tab is one component (`partials/student-documents-panel` + `-script`, `resources/css/student-documents.css`) included by both profiles; its routes are deliberately under `/health-records/*`, not `/adviser/*`, because `EnsureActiveSession` would switch a prototype nurse session over to `class_adviser` on an adviser URL. An open panel polls `student-documents.pulse` every 20s — a no-PII count+timestamp stamp, exempt in `AuditSensitiveAccess` like the adviser activity pulse — and re-reads the list only when the stamp moves, so each desk sees what the others just filed. The list endpoints return that same stamp alongside `documents`, so an uploader never re-fetches what it just rendered. Files go through `EncryptedFileStorage`; `StudentMedicalDocumentTest` guards upload/preview/download/delete, the cross-role list, and the per-school scoping.
- `ParentalConsentForm` — tracks deworming/program consent per student per school year. `ParentalConsentForm::currentSchoolYear()` computes the year dynamically.

### Frontend

Blade templates with Tailwind CSS 4. No Livewire. Alpine.js is used inline in some views. Vite bundles assets (`npm run build`). The condition search (`resources/views/components/condition-search.blade.php`) is a self-contained Alpine.js component that calls `GET /api/conditions`.

**LUSOG design system.** The Feeding Coordinator, the School Head and the School Nurse share one system; every page in those roles inlines three stylesheets **in this order**: `css/lusog-theme.css`, then its own page sheet (`css/feeding-*.css`, `css/schoolhead.css`, `css/school-nurse*.css`), then its rail sheet — `css/role-sidebar.css` for the coordinator/head `.asb-*` panel, `css/nurse-sidebar.css` for the nurse's logo-led `.sb-*` rail. `lusog-theme.css` owns the palette (`--lg-*`), the app shell, KPI cards, buttons, inputs, tables, the `.badge` status scale and the alert/flash components; a page sheet carries only what is unique to that page and must not redeclare shell or component rules. Green is the brand and the "healthy" signal only — amber is monitoring, orange at-risk, coral critical, teal neutral information; never paint a component green to look on-brand.

- Chart series come from `--series-healthy` / `--series-risk` in the theme (validated pair; re-run the dataviz validator before changing them).
- **Figures have one treatment, declared once.** `--lg-figures` (`tabular-nums lining-nums slashed-zero`) and `--lg-figure-features` in `lusog-theme.css` are applied by a single rule covering `.tnum`, `.num`, `.kpi-value`, `.kpi-hint`, `.badge` and number/date inputs — numbers in this app are read *down* a column (a roster of rates, a stack of KPIs, a BMI grid), and Inter's proportional default lets "1" narrow so a column of rates goes visibly ragged. All three features ship with Inter, so nothing extra loads and figures stay in the same voice as the rest of the UI. `--lg-mono` is the one monospaced stack, for places where a figure is the subject rather than a value in a sentence (the beneficiary record's value column reads it through `--bd-mono`). Set a figure's features by using those tokens, never by re-declaring `font-variant-numeric` on a page sheet.
- Every tab's `<h1 class="page-title">` is one line in two voices: the subject upright in DM Serif Display charcoal, then `<span>` with the section in italic emerald (`Dashboard <span>Feeding Program</span>`). The serif is loaded for page titles **only** — everything else is Inter.
- **School Nurse pages** use `partials/nurse-lusog-sidebar` and must include `partials/nurse-page-transition` (or an inline equivalent): `nurse-sidebar.css` starts `.sidebar ~ .main` at `opacity: 0` under `html.js`, so a page that never adds `.page-ready` renders blank. Deworming and Data Visualization are still on the retired `.nsb-*` rail (`partials/nurse-sidebar`); `NurseLusogShellTest` covers the converted tabs and `SchoolNurseDashboardTest` tracks the two that remain.

- The theme also declares `--asb-*` (sidebar) and `--ann-*` / `--clock-*` (announcements board, live-clock pill). Those partials and `role-sidebar.css` read every colour through `var(--token, <fallback>)`; the fallbacks now hold the same LUSOG values as the tokens, so a page cannot drift off-palette by failing to load them. Retheme by changing the token — edit a fallback only to keep it in step with its token, never to give one role a different colour.

**One palette, every role.** A page is on the palette one of two ways, never both: pages migrated to the design system inline `css/lusog-theme.css`; every other page inlines `css/lusog-palette.css` **after** its own styles, which re-points the older private ramps (`--g900`, `--text-3`, `--border`, …) at LUSOG values. Loading order is the whole mechanism — the palette wins by coming last, so a page that inlines it before its own `:root` silently keeps the old greens. Legacy sheets no longer hardcode hex greens; write new rules against `--lg-*`. `SharedPaletteTest` guards both the coverage and the ordering across all seven roles.

- Every role's rail shows the full `images/lusog-logo.png` lockup — the `.sb-logo-full` (nurse) or `.asb-logo-full` (all other roles) image, not an icon-plus-wordmark pair.
- The dashboard's BMI zone colours (`.grad-under/-healthy/-over` in `feeding-dashboard.css`) are a validated set, not a palette picked by eye. Re-run the dataviz validator before changing any of them — the brief's lighter `#F2B84B` / `#43A866` both fail the CVD and contrast checks as line colours.
- `feeding-sbfp-forms.css` deliberately keeps two registers: app chrome on the system, but `.form-sheet` and everything inside it is a facsimile of the printed DepEd form (black hairlines, uppercase heads). Do not modernise the sheet.

### Test Setup

PHPUnit with an in-memory SQLite DB (configured in `phpunit.xml`). Tests use `RefreshDatabase`. Feature tests directly boot the Laravel app — session state must be set manually via `$this->withSession([...])` since there is no Auth facade to log in with.
